# Embedded-Hardware-Atlas · 嵌入式硬件知识库

一个面向**嵌入式硬件工程师**的个人知识库：以 Obsidian 为载体，用「原始资料 → 分类整理 → Wiki 内化 → 思维模型」四层结构，系统沉淀电路原理、器件知识、PCB 工程方法与设计评审经验，并由 Git 进行版本管理。

- **规模**：630+ 篇 Markdown 笔记，200+ 份芯片手册 / 文献 PDF
- **覆盖**：模拟/数字电路、电源设计、信号完整性（SI/PI/EMC）、叠层与阻抗、PCB 模块化布局布线、器件手册解读
- **特点**：每篇 Wiki 页均有 frontmatter 与来源追溯（`sources`），状态分级（`seed / reviewed / needs-review`），事实与推断显式分离
- **维护方式**：用户提供原始资料与工程经验，AI Agent 按 `AGENTS.md` 规则负责整理、内化与索引（详见 [AGENTS.md](AGENTS.md)）

> ⚠️ 本库为个人学习与工程参考用途，不保证内容完全准确。所有器件参数以原厂最新数据手册为准，绝对最大额定值不可作为设计目标。

## 这个库解决什么问题

学硬件、做板子的过程中，知识天然是散落的：

| 痛点 | 本库的对策 |
|---|---|
| 视频课程看完就忘，无法检索 | 不按课程/集数组织，把知识点**拆出来重组成可检索的 Wiki 页** |
| 芯片手册几百页英文，每次都从头找 | 每颗器件一页**提炼**：关键参数、应用条件、限制与坑，原文留在原始层随时回查 |
| 踩过的坑过半年就忘 | 设计评审、失效模式、审查报告**沉淀成结构化页面**，下块板子直接复用 |
| 网上资料真伪难辨、版本混乱 | **来源追溯 + 状态分级**：结论必有出处，存疑显式标 `needs-review` |
| 经验零散、无法系统化 | 思维模型库提供**元方法层**，把散点经验挂到方法框架上 |

### 设计理念：四层流水线

```text
原始资料层（硬件/）        用户收集的手册、笔记、板卡资料 —— 只读存证
        ↓ 分类整理
分类整理层（硬件/原理、硬件/PCB）  按主题归类的有效来源 —— Wiki 的引用对象
        ↓ 知识内化
Wiki 层（wiki/）           结构化知识页：原理 / 器件 / PCB 方法 / 综合决策
        ↓ 方法提炼
思维模型层（思维模型库/）    通用思维方法论：第一性原理、5W2H、MECE、OODA…
```

每一层职责单一：原始层保证"证据还在"，分类层保证"来源可查"，Wiki 层保证"知识可用"，元方法层保证"分析方法论可迁移"。

### 诚实机制

知识库最常见的失败方式是"看起来很全，实际分不清哪些可信"。本库用三个机制对抗它：

1. **状态分级**：`seed`（草稿）→ `reviewed`（已核对来源）→ `needs-review`（存疑，引用前必须核验）；
2. **事实与推断分离**：页面上"手册原文说的"和"我推断的"分开写；
3. **不把绝对最大额定值当设计目标**：器件页中的参数边界永远区分为"绝对最大"与"推荐工作条件"。

| `index.md` | 公开导航 | 随内容更新 | 按问题进入全部知识页 |

### 内容组织原则

- **按知识主题组织，不按课程/视频/集数组织**——同一个知识点无论来自哪份资料，都收敛到同一篇 Wiki 页；
- **页面类型**由 frontmatter `type` 标定：`principle`（原理）/ `datasheet`（器件）/ `pcb-module`（模块电路）/ `pcb-method`（工程方法）/ `synthesis`（综合决策）/ `meta-method`（思维模型）/ `external-resource`（外来资源）；
- **每页必有来源**：`sources` 字段写明该结论出自哪些原始文件；`external/` 中的外来资料参与结论时，页面强制标记 `needs-review`；
- **命名**：器件页以器件型号命名（如 `PMW3901MB.md`），主题页以主题命名（如 `叠层阻抗.md`），审查报告带日期后缀（如 `单电调无人机原理图检查-2026-10-11.md`）；
- **私有边界**：`硬件/私人备份/` 仅本地保存，已由 `.gitignore` 排除，不出现在本仓库中。

## 如何使用

### 第一步：选择使用方式

| 方式 | 适合场景 | 操作 |
|---|---|---|
| **GitHub 网页浏览** | 快速查看、临时参考 | 直接浏览本仓库；用网页搜索框（按 `/` 聚焦）按文件名/关键词找页面；README 与各目录下的索引页可直接点击跳转 |
| **clone + 本地编辑器** | 经常查阅、不想装 Obsidian | `git clone https://github.com/xingkongtianxia/Embedded-Hardware-Atlas.git`；VS Code 用户建议装 Markdown All in One 插件获得大纲与预览；双链 `[[页面名]]` 无法跳转，用编辑器全局搜索替代 |
| **Obsidian 打开（推荐）** | 完整体验 | 见下方安装配置 |

**Obsidian 安装配置**（约 5 分钟）：

1. 从 [obsidian.md](https://obsidian.md) 下载安装（免费，个人用途不需要付费）；
2. 「打开文件夹作为仓库」→ 选择 clone 下来的 `Embedded-Hardware-Atlas` 目录；
3. 核心插件默认开启即可：**快速切换**（Ctrl+O）、**搜索**（Ctrl+Shift+F）、**反向链接**、**关系图谱**、**标签面板**；
4. 可选社区插件：`Dataview`（按 frontmatter 做动态表格，例如自动列出所有 `status: needs-review` 的页面）。

### 第二步：从入口开始，不要漫游

无论哪种方式，**入口永远是 [index.md](index.md)**：它是全库的内容目录，按主题与更新时间列出所有 Wiki 页链接，并标注每页的一句话摘要与状态。`index.md` 顶部还有"运行入口"一节，指向各板块的导航页（Wiki 概览、审查框架、来源映射、思维模型库索引、外来资源索引）。

### 按场景的使用流程

**场景 1：查一颗器件**（选型 / 核对参数 / 避坑）
1. 进 [wiki/原理/芯片手册](wiki/原理/芯片手册)，按器件类别找子目录（主控MCU / 电源管理 / 二极管与保护器件 / 无线通信 / 传感器 / 功率开关与驱动 / 存储器 / 显示与指示…）；
2. 读器件页的四类内容：**关键参数表**（工作电压、电流、封装、时序边界）、**应用条件**（外围电路要求、上电时序、典型拓扑）、**限制与坑**（如"文件名与实际型号不符""手册版本冲突""NTC 脚只接半边分压会锁死充电"）、**待确认项**；
3. 参数取值回到 `硬件/芯片数据手册/` 里的 PDF 原件核对——器件页是提炼，不是替代；
4. 该器件参与过的实际项目经验（如原理图审查结论）会通过双链出现在页面底部反向链接里，点进去看。

**场景 2：学一块电路 / 设计一个功能模块**
1. 进 [wiki/原理](wiki/原理) 对应主题（电源设计、SI、PI、EMC、叠层阻抗、模电、数电）；
2. 按 frontmatter 的 `status` 判断内容成熟度，优先读 `reviewed` 页；
3. 需要跨主题比较（如 LDO vs Buck 选型、光流+激光+气压融合定高方案）时，去 [wiki/综合](wiki/综合) 找决策框架页。

**场景 3：画 PCB / 做布局布线**
1. 进 [wiki/PCB](wiki/PCB)：`pcb-module` 类页面按功能模块（电源、时钟复位、高速接口、模拟采集、连接器保护、主控数字逻辑…）归纳布局、布线、测试要点与失效模式；
2. 通用方法（DFM、DFT、约束到放行检查、模块化布局）看 `pcb-method` 类页面；
3. 动手前对照 [wiki/综合/硬件设计审查框架]，把设计需求 → 原理 → PCB → 测试整条链路过一遍。

**场景 4：评审一块板子 / 排查一个问题**
1. 从 [wiki/综合/硬件设计审查框架] 进入，按检查清单逐项核对；
2. 涉及具体器件行为时跳转对应器件页，重点看"限制与坑"；
3. 需要系统化拆解问题时，用 [思维模型库/README](思维模型库/README.md) 选一个元方法（5-Whys 找根因、鱼骨图归因、假设-验证做实验设计、决策树做方案取舍…）。

**场景 5：系统性学习一个主题**
1. 先读该主题目录下的概览页（如 `wiki/原理/SI.md`）建立框架；
2. 再按反向链接 / 标签把该主题下的页面串起来读；
3. 用关系图谱（Obsidian Graph View）看这个主题的知识网络结构，找断点（没有链入的孤立页往往是最新的 `seed` 页）。

### 一次完整查询的示例演示

以"无人机要接 PMW3901 光流模块，怎么分配引脚"为例，走一遍标准流程：

1. **判定问题类型**：器件接入 + 引脚冲突 → 需要器件页 + MCU 资源分配知识；
2. **查器件页**：`wiki/原理/芯片手册/传感器/PMW3901MB.md` → 拿到硬边界：SPI ≤ 2MHz、VDD 1.8~2.1V / VDDIO 1.8~3.6V 且 VDDIO ≥ VDD、tWAKEUP 50ms、工作温度 0~40°C 室内级；
3. **查关联知识**：通过反向链接找到该页参与的综合页与审查报告；
4. **区分事实与推断**：手册数值是事实；"共享 SPI2 总线可行"是基于总线原理的推断，需验证；
5. **输出与验证**：产出引脚分配表，标注每条的依据（器件页 / 原理图取证 / 手册页码），存疑项单独列出；
6. **沉淀**：新结论写回知识库对应页面，更新索引与日志。

### 页面阅读规范

每篇 Wiki 页开头都有 frontmatter，字段含义：

| 字段 | 含义 | 用法 |
|---|---|---|
| `title` | 页面名称 | 全库唯一 |
| `type` | 页面类型 | 决定这页该往哪个目录放、按什么模板写 |
| `status` | 成熟度 | 引用可信度的第一判据，见下表 |
| `updated` | 最后更新日期 | 判断内容新旧 |
| `sources` | 原始出处 | 核验结论时回到这里 |
| `tags` | 检索标签 | 跨主题检索的辅助手段 |

**状态分级与引用规则**：

| status | 含义 | 引用规则 |
|---|---|---|
| `seed` | 初稿，刚摄入未核对 | 只作线索，不可直接引用 |
| `reviewed` | 已对照来源核对 | 可引用，仍建议关键取值回查 `sources` |
| `needs-review` | 存疑（来源冲突 / 型号不明 / 外来资料主导） | **引用前必须核验**，页内会写明存疑原因 |

### 检索技巧（Obsidian）

- `Ctrl + O` 快速切换：按页面名直接跳转；
- `Ctrl + Shift + F` 全库全文搜索：搜器件型号、关键词；

- GitHub 网页端：仓库首页搜索框输入关键词，用 "Go to file" 按文件名（器件型号）直达页面。

## 内容更新与维护规范

本库由用户与 AI 协作维护：用户负责提供原始资料与工程经验，AI 负责整理内化；所有变更遵循 `AGENTS.md` / [rules.md](rules.md) / [schema.md](schema.md)。

### 完整摄入流程（新资料进库）

1. **放入原始层**：新手册 / 资料 → `硬件/原始备份/`（器件手册 → `硬件/芯片数据手册/`），做哈希登记备份；
2. **分类整理**：按主题归入 `硬件/原理/` 或 `硬件/PCB/` 的对应分类稿，更新 `分类与来源摘要.md`；
3. **建 Wiki 页**：按页面类型模板写正文，frontmatter 齐全，状态从 `seed` 起步；
4. **登记来源映射**：在 `wiki/来源映射.md` 记录"原始文件 ↔ Wiki 页"的对应关系；
5. **更新索引与日志**：`index.md` 加条目（含一句话摘要），`log.md` 追加变更记录；
6. **写当日日志**：`journal/daily/YYYY-MM-DD.md`（每日最多一份，含工作日志 + 下一步计划）。

### 变更规范速查

| 动作 | 规范 |
|---|---|
| **新增原始资料** | 只放进 `硬件/原始备份/`（或 `硬件/芯片数据手册/`），不可修改已有文件 |
| **新增 Wiki 页** | 必须含 frontmatter（title / type / status / updated / sources / tags），状态从 `seed` 起步 |
| **状态流转** | `seed`（草稿）→ `reviewed`（已核对来源）→ 内容存疑时回退 `needs-review` |
| **登记外来资源** | 在 `external/` 建条目，必须写 URL、获取日期、作者/机构、可靠性、许可、待核验项 |
| **变更留痕** | 每次摄入/修改后同步更新 `index.md`、追加 `log.md`、写当日 `journal/daily/YYYY-MM-DD.md` |
| **健康检查** | 定期运行：核对来源可追溯、双链有效、哈希一致、发布边界（私人资料未入库），报告存 `journal/` |
| **版本管理** | Git 管理；提交前核验 `.gitignore`，确保私人资料与临时文件不入库 |

### Wiki 页写作模板

正文按页面类型组织，共同要求：**结论前置、分节清晰、每个硬数字有出处、坑和限制单列**。器件页（`datasheet`）典型结构：

```markdown
## 关键参数（表格：参数 / 最小 / 典型 / 最大 / 出处页码）
## 应用条件（外围电路、上电时序、典型拓扑）
## 限制与坑（✅ 已验证 / ⚠️ 存疑，逐条列出）
## 待确认项（型号 / 版本 / 冲突点）
## 关联页面（双链）
```

## 常见问题（FAQ）

**Q：为什么有些页面标着「待复核」？**
`needs-review` 是本库的诚实机制：来源存在冲突、型号/版本不明、或结论主要由外来资料支撑时，页面会被显式标记，提示引用者先自行核验。

**Q：wiki 里的器件页能替代官方数据手册吗？**
不能。器件页是对手册的提炼（关键参数、应用边界、易错点），只做导航与速查；设计取值一律以原厂最新手册为准。

**Q：怎么判断一篇内容的新旧与可信度？**
看 frontmatter：`updated` 判断新旧，`status` 判断可信度；`sources` 给出核验路径。

**Q：为什么用 Obsidian 而不用 Notion / 语雀？**
本地 Markdown + Git：文件归自己、可版本管理、双链开放标准、AI 可直接读写。Notion 类云端方案在这些维度上都不满足。

**Q：为什么按主题组织而不是按课程/视频顺序？**
课程顺序服务于"听讲"，不服务于"检索"。同一知识点（比如去耦电容摆放）可能出现在三门课里，但库中只有一篇页面，三门课的要点都收敛进去。

**Q：PDF 手册原件在哪里？**
`硬件/芯片数据手册/`（及 `硬件/原始备份/`），按器件名命名。仓库体积因此较大，clone 需要一些时间。

**Q：为什么仓库里没有某些我在本地见过的目录？**
`硬件/私人备份/` 等私有内容已被 `.gitignore` 排除，仅存在于本地。

**Q：Excalidraw 目录是什么？**
手绘示意图（.excalidraw.md），配合 Wiki 页解释拓扑结构，可用 Obsidian Excalidraw 插件查看与编辑。

**Q：可以转载 / 复用本库内容吗？**
Wiki 正文与结构化笔记可参考、复用，请注明出处；`硬件/` 与 `external/` 下的原厂手册、第三方文献版权归原权利人所有，本库仅作个人学习存档。

**Q：如何贡献或纠错？**
这是个人知识库，暂不接受 PR；发现错误欢迎提 Issue。

## 公开与私人边界

工作日志（`journal/daily/`）、规划库（`journal/planning/`）、维护时间线（根`log.md`）和`硬件/私人备份/`仅在唯一知识库本地保留，由`.gitignore`持续排除。公开导航与清单不引用这些私人内容。

维护流程中记录日志/计划指本地操作，不代表上传授权。撤下只影响当前版本与未来提交，历史已发布提交不会自动清除。

提交前运行`python scripts/check_kb.py`；暂存完成后运行`python scripts/check_kb.py --staged`验证将要提交的实际内容。检查覆盖来源层、哈希、双链、索引可达性与私人文件跟踪；体检警告不能当作已解决。
